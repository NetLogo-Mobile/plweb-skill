# 分页与查找目标

## 按时间翻页

`Skip` 传跳过条数无效，会反复返回同一页；不能按 `0、20、40` 递增分页，也不能把重复页当作新的搜索结果。作品列表通过 `Query.From` 沿时间方向续页。

1. 第一页 `From=null`、`Skip=0`，通常 `Take=20`。保持分类、作者、标签、语言和排序条件一致。
2. 2026-10-30 使用授权账号实测：当前 `/Contents/QueryExperiments` 的 `Query.From` 接受上一页末尾作品的摘要 `ID` 字符串作为时间方向的游标；传 `SortingDate` 的毫秒数、毫秒数字字符串或 ISO 时间字符串都返回 `Input.Field.Invalid`。因此发送 `From=上一页末条.ID`，同时记录对应的 `SortingDate` 以检查时间是否推进。不要把“按时间翻页”误写成直接发送原始时间值。
3. 后续请求仅推进 `From`，`Skip` 保持 0。按摘要 `ID` 去重，并记录游标、已检查的时间范围和新增条数。用户给出起止时间时，用返回的 `SortingDate` 判断候选是否落入区间；不要编造时间转 ID 的编码规则。其他排序组合先检查实际推进方向，不假定所有组合都支持续页。
4. 遇空页、相同游标或整页没有新增 ID 时停止，报告边界或重复问题；不要无限重试、通过改 `Skip` 碰运气，或随意把时间减一跳过同时间的数据。不能保证已取完同一时间戳下的全部记录时，说明这一限制。
5. 评论已核对：CommentID 传上一页末条 ID、Skip=0，边界包含需按 ID 去重；可用 fetch_comments 自动循环。对通知、关系、支持者等其他列表，不能假定 `Skip` 是条数偏移。仅当该接口已核对游标的位置、格式与时间语义时才续页；否则先读首批并说明范围，不能擅自给接口补 `From`、借用作品分页协议或宣称已遍历全部。若新版本接口确实接受直接的时间参数，应先做一次有界的读取测试，验证无重复且时间推进，再记录其准确格式。

## 没有名称搜索接口时怎样找东西

支持 `/Users/GetUser` 的 `Name` 完整昵称精确定位：2026-10-31实测返回对应用户；截短昵称未命中。关系列表的 `Query` 可在所查关系范围按完整昵称筛选，本次样本截短昵称未命中。尚未确认全站模糊用户名或作品标题搜索接口，不得发明 `/Search`、`Keyword`、`SearchText`、`Subject` 等搜索参数。

- **先利用直接定位信息。** 从用户给出的作品/主页链接、已有对象、评论或通知中提取摘要 ID、保存 ID、用户 ID；按已知 ID 读取对象，再核对标题、昵称和作者。不要把显示名当 ID。
- **找作品。** 没有作品 ID 时，先利用已知作者 ID、分类、标签、语言、发布时间范围缩小作品列表；用 `QueryExperiments` 按时间分页获取候选，在本地对 `Subject`、可用的 `LocalizedSubject` 和必要的介绍文本做匹配。先比对完整标题，再比对包含词或用户给出的关键词；相似项只是候选，不能自动认定为目标。
- **找用户。** 已知完整昵称先用GetUser(Name)，再核对ID、简介和作品；不能把单次返回当作重名唯一性证明。只知部分昵称时，先检查已有作品摘要的 `User`、评论作者、通知参与者，以及有依据的主页、关注/粉丝列表，收集用户 ID 与昵称；在这些已取回的数据中匹配昵称，再用 `/Users/GetUser` 的 `ID` 读取核验。知道某个作品时优先从作者反查；知道某位相关用户时可查有界的关系候选。不要从全站作品无限爬取来冒充用户名搜索。
- **同名与改名。** 昵称不唯一，标题也可能重复；结合用户 ID、作者、头像/简介、作品内容和时间核对。有多个合理候选时列出少量候选及区分信息，由用户选择，不能对模糊匹配的对象直接写入。
- **控制范围并如实报告。** 优先采用用户提供的线索；线索不足时先检查与当前上下文有关的少量页面（默认最多 5 页），记录检查了哪些分类、作者和时间范围。仍找不到时说明“在本次检查范围内未找到”，再索取作品链接、作者、分类、时间或更完整标题。不能报告全站不存在，也不能声称服务端执行了名称搜索。继续扩大范围应与用户需求相称。

这是“取回候选后在本地筛选”，不是社区提供的名称搜索。任何管理、发评论、扣币或编辑之前，都必须通过 ID 核实最终对象。
